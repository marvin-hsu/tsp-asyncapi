# Protobuf payload

帶有官方 `TypeSpec.Protobuf` decorator 的 model，可以用整個 package 的 proto3 文字當作 AsyncAPI payload。本頁說明如何開啟，以及會寫出什麼。

::: warning
這是預覽功能，預設關閉。開啟它的選項、寫出的 schema，以及回報的診斷，都可能在次版本變更。
:::

## 這個功能做什麼

[`@typespec/protobuf`](https://www.npmjs.com/package/@typespec/protobuf) 把 model 描述成 Protobuf message。它自己的 emitter 會把 model 寫成 `.proto` 檔案。

本 emitter 對同一批 model 執行同一個套件，取得 proto3 文字，寫進 AsyncAPI message 的 payload。所以資料只描述一次，兩份產出不會各自漂移。

沒開這個功能時，官方 decorator 在這裡不造成任何差異。那些 model 會和其他 model 一樣轉成 JSON Schema。

## 開啟方式

先在本 emitter 旁邊安裝官方套件。

```bash
npm install @typespec/protobuf
```

再於 `tspconfig.yaml` 指名這個功能。

```yaml
emit:
  - "tsp-asyncapi"

options:
  "tsp-asyncapi":
    preview-features: ["protobuf"]
```

[`preview-features`](../reference/emitter-options#預覽功能) 的保留名稱是 `protobuf` 與 `avro`。本版只有 `protobuf` 有對應的實作。請求 `avro` 會回報 [`preview-feature-unavailable`](../reference/diagnostics#preview-feature-unavailable)，而且不寫出任何檔案。

## 撰寫來源

下面這份是 repository 裡的 [`examples/16-protobuf-payloads`](https://github.com/marvin-hsu/tsp-asyncapi/tree/main/examples/16-protobuf-payloads)。同一個 Protobuf package 的兩個 model，走兩個 channel 送出。

```typespec
import "tsp-asyncapi";
import "@typespec/protobuf";

using AsyncAPI;

@service(#{ title: "Orders Service" })
@info(#{
  version: "1.0.0",
  description: "Order events, carried as protobuf on Kafka.",
})
namespace OrdersService;

@Protobuf.package({ name: "com.example.orders" })
namespace Contracts {
  /**
   * One order a customer placed.
   */
  @message
  @Protobuf.message
  model OrderPlaced {
    @Protobuf.field(1)
    orderId: string;

    @Protobuf.field(2)
    amountCents: int32;
  }

  /**
   * One order that left the warehouse.
   */
  @message
  @Protobuf.message
  model OrderShipped {
    @Protobuf.field(1)
    orderId: string;

    @Protobuf.field(2)
    carrier: string;
  }
}

@channel("orders.placed")
interface Placed {
  @send
  op placed(event: Contracts.OrderPlaced): void;
}

@channel("orders.shipped")
interface Shipped {
  @send
  op shipped(event: Contracts.OrderShipped): void;
}
```

作用域裡有兩個叫 `message` 的 decorator。`@message` 是 AsyncAPI 的，把 model 標記成文件的一個 message。`@Protobuf.message` 把同一個 model 標記成 `.proto` 檔案的一個 message。Protobuf 那個要寫完整名稱。

`@Protobuf.package` 標記哪一個 namespace 會變成一個 `.proto` 檔案。裡面的名稱是該檔案的 `package` 宣告，與 TypeSpec namespace 的名稱無關。

## emitter 寫出什麼

payload 是 [Multi Format Schema Object](https://www.asyncapi.com/docs/reference/specification/v3.0.0#multiFormatSchemaObject)。`schemaFormat` 指名 proto3，`schema` 放文字內容。

```yaml
components:
  schemas:
    OrderPlacedPayload:
      schemaFormat: application/vnd.google.protobuf;version=3
      schema: |
        // Generated by Microsoft TypeSpec

        syntax = "proto3";

        package com.example.orders;

        // One order a customer placed.
        message OrderPlaced {
          string orderId = 1;
          int32 amountCents = 2;
        }

        // One order that left the warehouse.
        message OrderShipped {
          string orderId = 1;
          string carrier = 2;
        }
  messages:
    OrderPlaced:
      name: OrderPlaced
      description: One order a customer placed.
      payload:
        $ref: "#/components/schemas/OrderPlacedPayload"
    OrderShipped:
      name: OrderShipped
      description: One order that left the warehouse.
      payload:
        $ref: "#/components/schemas/OrderPlacedPayload"
```

一個 message 的 payload 是整個 package 的文字，不是單一 message 的片段。要讀懂一份 `.proto` 檔案，需要 `syntax` 那一行、`package` 那一行，以及該檔案的每一個宣告。

上面兩個 model 屬於同一個 package，所以兩份 payload 是同一段文字。emitter 把那段文字寫進 `components.schemas` 一次，再讓兩個 message 指向它。每一種以其他語言撰寫的 schema 都適用這條規則。元件如何命名，見[可重用元件參考](../reference/reusable-components)。

## 同時寫出 `.proto` 檔案

兩個 emitter 各自獨立。專案若也需要磁碟上的檔案，在 `emit` 同時列出兩個。

```yaml
emit:
  - "tsp-asyncapi"
  - "@typespec/protobuf"

options:
  "tsp-asyncapi":
    preview-features: ["protobuf"]
  "@typespec/protobuf":
    emitter-output-dir: "{project-root}/proto"
```

官方 emitter 於是寫出 `proto/com/example/orders.proto`。

```proto
// Generated by Microsoft TypeSpec

syntax = "proto3";

package com.example.orders;

// One order a customer placed.
message OrderPlaced {
  string orderId = 1;
  int32 amountCents = 2;
}

// One order that left the warehouse.
message OrderShipped {
  string orderId = 1;
  string carrier = 2;
}
```

本 emitter 不讀那個檔案。它在記憶體裡執行官方 emitter 並留下文字。所以不論檔案有沒有寫出，payload 都一樣。

## Protobuf 沒有描述的部分

Protobuf 描述資料。它沒有描述 message 走哪一個 channel、message 的方向，也沒有描述應用的 operation。

所以 `@channel`、`@send`、`@receive` 與 `@message` 仍然必要。只帶 `@Protobuf.message` 而沒有 `@AsyncAPI.message` 的 model 不會拿到 payload，也不會回報任何診斷。

## 作者手寫的 payload

[`@rawPayload`](../reference/decorators/messages#rawpayload) 用來手寫其他語言的 schema。那是作者的明示宣告，所以優先於產生的 schema。

同時帶兩者的 model 會回報 [`conflicting-message-schema-source`](../reference/diagnostics#conflicting-message-schema-source)。文件保留作者手寫的 schema。要改用產生的 schema，就從該 model 移除 `@rawPayload`。

## 取不到文字的情況

產生的 payload 有可能不存在。model 上方可能沒有 `@Protobuf.package`。官方 emitter 可能拒絕轉換該 model。它也可能對整個程式都沒有寫出內容。

以上每一種都會回報 [`protobuf-artifact-unavailable`](../reference/diagnostics#protobuf-artifact-unavailable)，訊息會說明是哪一種。emitter 選擇回報問題，而不是寫出空的 payload，因為空的 payload 讀起來像是什麼都沒描述的 schema。
