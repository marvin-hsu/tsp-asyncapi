# Protobuf Payloads

A model that carries the official `TypeSpec.Protobuf` decorators can get the proto3 text of its package as its AsyncAPI payload. This page shows how to turn that on and what it writes.

::: warning
This is a preview feature. It is off by default. The option that turns it on, the schema it writes, and the diagnostics it reports can change in a minor release.
:::

## What it does

The [`@typespec/protobuf`](https://www.npmjs.com/package/@typespec/protobuf) library describes a model as a Protobuf message. Its own emitter writes that model out as a `.proto` file.

This emitter runs the same library over the same models. It takes the proto3 text and writes it as the payload of the AsyncAPI message. So one source describes the data once, and the two artifacts cannot drift apart.

Without the feature the official decorators change nothing here. The models lower to JSON Schema, the way every other model does.

## Turning it on

Install the official library next to this emitter.

```bash
npm install @typespec/protobuf
```

Then name the feature in `tspconfig.yaml`.

```yaml
emit:
  - "tsp-asyncapi"

options:
  "tsp-asyncapi":
    preview-features: ["protobuf"]
```

The reserved names of [`preview-features`](../reference/emitter-options#preview-features) are `protobuf` and `avro`. Only `protobuf` has a provider in this release. A request for `avro` reports [`preview-feature-unavailable`](../reference/diagnostics#preview-feature-unavailable), and nothing is written.

## Writing the source

The example below is [`examples/16-protobuf-payloads`](https://github.com/marvin-hsu/tsp-asyncapi/tree/main/examples/16-protobuf-payloads) in the repository. Two models of one Protobuf package are sent over two channels.

```typespec
import "tsp-asyncapi";
import "@typespec/protobuf";

using AsyncAPI;

@service(#{ title: "Orders Service" })
@info(#{
  version: "1.0.0",
  description: "Order events, carried as protobuf on Kafka.",
})
namespace OrdersService;

@Protobuf.package({ name: "com.example.orders" })
namespace Contracts {
  /**
   * One order a customer placed.
   */
  @message
  @Protobuf.message
  model OrderPlaced {
    @Protobuf.field(1)
    orderId: string;

    @Protobuf.field(2)
    amountCents: int32;
  }

  /**
   * One order that left the warehouse.
   */
  @message
  @Protobuf.message
  model OrderShipped {
    @Protobuf.field(1)
    orderId: string;

    @Protobuf.field(2)
    carrier: string;
  }
}

@channel("orders.placed")
interface Placed {
  @send
  op placed(event: Contracts.OrderPlaced): void;
}

@channel("orders.shipped")
interface Shipped {
  @send
  op shipped(event: Contracts.OrderShipped): void;
}
```

Two decorators named `message` are in scope. `@message` is the AsyncAPI one, and it marks a model as a message of the document. `@Protobuf.message` marks the same model as a message of the `.proto` file. Write the Protobuf one qualified.

`@Protobuf.package` marks the namespace that becomes one `.proto` file. The name in it is the `package` declaration of that file, and it is independent of the TypeSpec namespace name.

## What the emitter writes

The payload is a [Multi Format Schema Object](https://www.asyncapi.com/docs/reference/specification/v3.0.0#multiFormatSchemaObject). `schemaFormat` names proto3, and `schema` holds the text.

```yaml
components:
  schemas:
    OrderPlacedPayload:
      schemaFormat: application/vnd.google.protobuf;version=3
      schema: |
        // Generated by Microsoft TypeSpec

        syntax = "proto3";

        package com.example.orders;

        // One order a customer placed.
        message OrderPlaced {
          string orderId = 1;
          int32 amountCents = 2;
        }

        // One order that left the warehouse.
        message OrderShipped {
          string orderId = 1;
          string carrier = 2;
        }
  messages:
    OrderPlaced:
      name: OrderPlaced
      description: One order a customer placed.
      payload:
        $ref: "#/components/schemas/OrderPlacedPayload"
    OrderShipped:
      name: OrderShipped
      description: One order that left the warehouse.
      payload:
        $ref: "#/components/schemas/OrderPlacedPayload"
```

The payload of a message is the text of its whole package, not the fragment of one message. A reader of a `.proto` file needs the `syntax` line, the `package` line, and every declaration the file holds.

Both models above belong to one package, so both payloads are the same text. The emitter writes that text once under `components.schemas` and points both messages at it. That is the rule for every schema written in another language. The [Reusable Components reference](../reference/reusable-components) says how the component is named.

## Emitting the `.proto` file as well

The two emitters are independent. List both in `emit` when the project also needs the file on disk.

```yaml
emit:
  - "tsp-asyncapi"
  - "@typespec/protobuf"

options:
  "tsp-asyncapi":
    preview-features: ["protobuf"]
  "@typespec/protobuf":
    emitter-output-dir: "{project-root}/proto"
```

The official emitter then writes `proto/com/example/orders.proto`.

```proto
// Generated by Microsoft TypeSpec

syntax = "proto3";

package com.example.orders;

// One order a customer placed.
message OrderPlaced {
  string orderId = 1;
  int32 amountCents = 2;
}

// One order that left the warehouse.
message OrderShipped {
  string orderId = 1;
  string carrier = 2;
}
```

This emitter does not read that file. It runs the official emitter into memory and keeps the text. So the payload is the same whether the file is written or not.

## What Protobuf does not describe

Protobuf describes the data. It says nothing about the channel a message travels on, the direction of a message, or the operations of an application.

So `@channel`, `@send`, `@receive` and `@message` are still required. A model that carries `@Protobuf.message` and no `@AsyncAPI.message` gets no payload and reports nothing.

## A payload the author wrote by hand

[`@rawPayload`](../reference/decorators/messages#rawpayload) writes a schema in another language by hand. It is an explicit statement, so it wins over a generated one.

A model that carries both reports [`conflicting-message-schema-source`](../reference/diagnostics#conflicting-message-schema-source). The document keeps the authored schema. Remove `@rawPayload` from the model to take the generated one.

## When no text is available

A generated payload can be missing. The model can have no `@Protobuf.package` above it. The official emitter can refuse to convert the model. It can also write nothing for the whole program.

Each of these reports [`protobuf-artifact-unavailable`](../reference/diagnostics#protobuf-artifact-unavailable), and the message says which one it is. The emitter reports the problem instead of writing an empty payload, because an empty payload reads as a schema that describes nothing.
